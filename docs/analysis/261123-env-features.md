# Analysis: env-features anchors (2026-11-25)

Status: read-only investigation. Nothing in the repo was changed to produce it. Where a finding disagrees with the plan input, the finding wins. The disagreements are listed in the section "Plan changes".

Method: read each anchor file on branch `002-env-features` (clean tree, same as `main`). Upstream facts come from the raw source of `tailscale/codespace`, `devcontainers/cli` v0.88.0, `devcontainers/spec`, `tailscale/tailscale`, and from `npm view` and `ctx7`.

## A1. scripts/verify.sh

- `fast()` finds shell files with `git ls-files` and the pattern `\.sh$|^src/orca-server/orca-server$|^test/_global/tailscale_stub/tailscale$`. Only orca-server's extensionless script is named. A new Feature script with a `.sh` suffix is already covered.
- `fast()` runs the FR-024 constant check on `src/orca-server/install.sh` and `src/orca-server/devcontainer-feature.json` only. Pairs checked: `version:DEFAULT_VERSION` and `debSha256:DEFAULT_DEB_SHA256`.
- `fast()` runs the style scan (dash, emoji, US spelling) on `docs`, `specs`, `README.md` and every `src/**/NOTES.md`. New NOTES.md files are covered with no change.
- `default_test()` runs `dc features test -p . -f orca-server -i <base image> --skip-scenarios`.
- `scenarios()` copies `src` and `test/orca-server` to a temp dir, replaces `__BASE__` in `test/orca-server/scenarios.json`, and runs `dc features test -f orca-server --skip-autogenerated`.
- `ci` loops three bases, runs `default_test` and `scenarios`, then `dc features test -p . --global-scenarios-only`, then `test/orca-server/build-fails.sh` and `test/orca-server/secrets_scan.sh`.
- `build-fails.sh` and `secrets_scan.sh` copy `src/orca-server` by name. They are orca-server tests, not generic ones.
- `test/verify-fast-untracked.sh` copies `scripts/verify.sh` into a temp git repo with no `src/`. A generalised `fast()` must still pass there.

## A2. .github/workflows/release.yaml

- The trigger is `on: push: branches: [main]`. There is **no `paths` filter**. The input said "paths filter is src/orca-server/** only". That is not what the file says.
- The `publish` job uses `devcontainers/action` with `base-path-to-features: ./src`. The action publishes every Feature under `./src` and skips a version that is already published.
- Result: release.yaml already runs on any push to main, which includes any change under `src/`. It already publishes every Feature.
- AC10 holds today as a superset. A `paths: ['src/**']` filter would narrow the trigger and stop the `test` job running on a push that changes only `scripts/` or `test/`.

## A3. .github/workflows/test.yaml

- The validate step uses `base-path-to-features: ./src`. It covers every Feature. No change.
- The `test` job runs `bash scripts/verify.sh ci` with `timeout-minutes: 120`. Four Features on three bases will take longer than one. See "Risks".

## A4. src/orca-server/devcontainer-feature.json, install.sh, entrypoint.sh

- `installsAfter` holds two full OCI ids: `ghcr.io/tailscale/codespace/tailscale` and `ghcr.io/devcontainers-extra/features/tailscale`. The new entry follows the same form: `ghcr.io/flumpiey/devcontainer-features/tailnet`.
- Feature `version` is `1.0.1`. The action skips a published version, so a metadata change that ships needs a bump.
- `install.sh` OS check: `case "$os_id:$os_version_id:$arch"` with `debian:12:x86_64 | ubuntu:22.04:x86_64 | ubuntu:24.04:x86_64`, error via `fail 1`. `os_field` reads `/etc/os-release` in a subshell. One error line, names the bases.
- `DEFAULT_VERSION` and `DEFAULT_DEB_SHA256` are constants at the top, equal to the JSON defaults.
- `entrypoint.sh` sets `umask 077`, traps ERR to `exec "$@"`, starts the service with `setsid ... &`, and ends with `exec "$@"`.

## A5. test/_global and test/orca-server

- `test/_global/scenarios.json` has one scenario, `tailscale_stub`. It builds `test/_global/tailscale_stub/Dockerfile`, which copies a stub `tailscale` into `/usr/local/bin`, and installs only orca-server and sshd.
- The stub ignores its arguments. It prints `NoState` for 15 seconds after the first call, then `Running` with a DNS name.
- orca-server's scenario does not install the real Tailscale Feature, so the stub is never overwritten. A tailnet scenario does install it (hard dependency), and the real Feature's `install.sh` writes `/usr/local/bin/tailscale`. The stub must therefore sit earlier on `PATH`, not replace that file. See finding B3.
- Patterns to reuse: `source dev-container-features-test-lib`, `check`, `reportResults`; `install_twice.sh` re-runs the mounted `install.sh` as root; `secrets_scan.sh` builds with the CLI and greps `docker history`; `build-fails.sh` runs `expect_fail` per bad input.
- `secrets_scan.sh` greps `TS_AUTH_KEY` as a literal word. tailnet stores the variable **name** in its options file, so a literal-name grep would fail the scan. The tailnet scan must grep for a canary key value instead.

## Findings from upstream (full record in research.md)

- B1. Feature entrypoints are not chained by `exec "$@"`. The CLI writes them one per line into one `/bin/sh -c` script, runs them in sequence, then runs `exec "$@"` itself. Each entrypoint is a blocking child. Source: `devcontainers/cli` v0.88.0, `src/spec-node/singleContainer.ts` lines 389 to 393.
- B2. The upstream Tailscale Feature entrypoint already starts `tailscaled` and, when `TS_AUTH_KEY` is set, runs a blocking `tailscale up --accept-routes --authkey=...` with no hostname, no tags and no SSH. It then unsets `TS_AUTH_KEY` in its own child. It already declares `capAdd` `NET_ADMIN`, `NET_RAW`, `MKNOD`. Sources: `tailscaled-entrypoint.sh`, `tailscaled-devcontainer-start.sh`, `devcontainer-feature.json` (version 1.0.8).
- B3. With B1, tailnet's entrypoint runs after the upstream one in the same wrapper, and still sees `TS_AUTH_KEY`, because the unset happened in the upstream child. tailnet therefore runs `tailscale up` a second time on a node that may already be `Running`.
- B4. `tailscale set` has `--ssh` and `--hostname` but no tags flag. Tags need `tailscale up --advertise-tags`.
- B5. The npm package `typescript@7.0.2` is `latest` and its binary is `tsc`. A global install would put a TypeScript 7 `tsc` on `PATH`. `@typescript/native-preview` (binary `tsgo`) is a stale preview (`7.0.0-dev.20260707.2`).
- B6. Vitest reads `VITEST_MAX_WORKERS`. Jest has no environment variable for worker count. It uses `--maxWorkers` or config.

## Plan changes

1. release.yaml: no change to the trigger. The input's anchor was wrong. Add a `fast` check that release.yaml has no `paths:` filter that excludes `src/**`. AC10 stays satisfied.
2. tailnet: capAdd is not declared. The hard dependency already adds `NET_ADMIN`, `NET_RAW` and `MKNOD`. The data-model input listed it; the finding removes it.
3. tailnet: the entrypoint expects the upstream join may already have happened. It runs `tailscale up --reset --accept-routes --ssh --hostname=... --advertise-tags=...`, not a bare first join.
4. ts7-cli: a plain global install would shadow the repo's `tsc`. The package installs into a private prefix and exposes the binary as `tsc7`.
5. node-guard: the test-runner worker limit is `VITEST_MAX_WORKERS=1`. Jest has no variable. NOTES.md says so.
6. orca-server: a second line changes. `version` goes from `1.0.1` to `1.0.2`, or the `installsAfter` change never publishes.
7. verify.sh: `build-fails.sh` and `secrets_scan.sh` run per Feature where the file exists. tailnet adds its own `secrets_scan.sh` with a canary key.

## Risks

- `ci` time: orca-server has 8 scenarios per base. Adding three Features raises the run time. The 120 minute job timeout may not hold.
- AC1 needs a real tailnet join and `/dev/net/tun`. CI cannot do either. The stub proves the arguments, not the join.
- A Feature `containerEnv` of `${containerWorkspaceFolderBasename}` is substituted at container creation by CLI code that reads the metadata label. Not run here. The slice 4 test proves it, with a `/workspaces/*` fallback.
